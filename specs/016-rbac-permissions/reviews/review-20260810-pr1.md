## Important (3 → 2 root causes) — all FIXED

### I-1 · Stale `isStaffRole` shadow in `change-role.ts` (found by 3 lenses; CONFIRMED)

`src/modules/auth/application/change-role.ts:55-57` carried a private
`isStaffRole = role === 'admin' || role === 'manager'`, a duplicate of the Domain helper.
PR 1 widened `STAFF_ROLES` to four staff roles, so the copy silently began classifying
`super_admin` and `marketing` as **member-side**. Line 71 uses it as the staff↔member portal
boundary, so the invariant would have **failed open** for exactly the roles this feature adds
— with no compile-time signal, because the parameter type is `Role`. Reachable in the very next
window (the D18 pre-minted super_admin), not only after marketing exists.

**Fix**: deleted the shadow; `change-role.ts` now imports the Domain `isStaffRole`.
**Tripwire added**: `tests/unit/auth/application/change-role-portal-boundary.test.ts` — 20 cases
over all five roles (every staff→member and member→staff refused with `role-portal-mismatch`;
every staff→staff permitted, which Migration C's promotion and its demotion rollback depend on).

### I-2 · Invoice-settings form derives editability from `role === 'admin'` (CONFIRMED)

`invoice-settings-form.tsx` computed `isAdmin = currentUserRole === 'admin'`, driving the
disabled state, the dirty check, the submit guard and the action row. PR 2 gates that page on
`settings.invoicing`, which per D3 is **super_admin-only** — so the only role permitted to edit
would have received a permanently disabled form. The PR-1 cast on the page suppressed the type
error that would otherwise have surfaced this.

**Fix**: the prop is now a server-derived `canEdit: boolean` (never a role literal in the client);
the page passes `canEdit={currentUser.role === 'admin'}` today and becomes
`hasPermission(role, 'settings.invoicing', …)` in PR 2 with **no change to the component**.
Four call sites in the component and six in its tests updated.

## Deferred with rationale (not defects in PR 1)

- **`rbac-2` / `rbac-3` / `rbac-5` — deny-by-exclusion (`role === 'member'`) rather than
  allow-list, in the activity feed, directory export and credit-note page.** All three verifiers
  established the failure is unreachable: no `marketing` row can exist (both server zod enums are
  still 3-valued, now pinned by M-6), and the one role that does become real in this window —
  the D18 super_admin — gets the **correct** answer at each site per design § 4.1. Critically,
  "fixing" them now with a literal `admin || manager` allow-list would **wrongly deny super_admin**
  from PR 3 onward. These are exactly the call sites PR 2 converts to
  `requireApiPermission` / `requirePagePermission`, which is where the fix belongs.
- **`i18n-2` — users role filter hardcodes the pre-016 three roles.** Correct for PR 1: the roles
  are not assignable, so there are no rows to filter. PR 3 widens it with the picker.
- **`dup-1` — role labels now have four sources of truth** (2 i18n namespaces, the email
  `ROLE_LABELS`, and the TS `Record<Role>` maps); only the TypeScript ones are exhaustiveness-checked.
  Real structural observation; consolidation belongs with the PR-3 users-page retrofit (T048).
- **`type-4` / `type-5` — the injectable `bundles` seam on the production signature and
  `getPermissionSet`'s inability to express the flag-OFF leg.** Both are deliberate PR-1 shapes:
  the seam is what makes the E2 poisoned-bundle proof possible without module mocking, and
  nav filtering under the flag is PR-2 work (§ 6.1 third surface).
- **`test-4` header claim** that the flag-parameterised CI job exists — it is deferred to PR 2 with
  the reason recorded in `tasks.md` T002 (the evaluator takes the flag as a parameter, so both legs
  already run in one pass; an env matrix only becomes meaningful once `src/lib/rbac.ts` reads env).
