## The root cause, stated once

`buildAudienceTick` was written as a clean 400-line sibling of `dispatchScheduledBroadcast`
(1,200 lines) and **dropped four things the older path had accumulated across five review
rounds**: terminal transition on resolver refusal, the FR-021 member notification, the
`failureReason` write, and the `GatewayThrowable` catch with a retry budget.

`tsc` cannot see a missing `applyTransition`. Unit tests that assert only `error.kind` cannot
see it either. Three agents reached this conclusion independently from three different symptoms.

**The single number that summarises the review:**

## The class grep cannot find

S55 and S56 are a different kind of finding from everything above them, and they arrived last,
from the eighth reviewer. Every other finding is **a dropped call site** — `applyTransition`,
`safeAuditEmit`, `failedToDispatchCount`, the FR-021 enqueue. Those have names. Comparing the
two files, or grepping for the name, finds them.

These two are **a port narrower than the capability.** The thing that went missing has no name
in the new file to grep for, because the *type* refuses to carry it:

```ts
/** What the resolver answers, narrowed to what this use case reads. */
export interface ResolvedAudience {
  readonly recipients: readonly string[];
  readonly estimatedCount: number;
}
```

That docblock is the whole problem. It reads as careful interface design — take only what you
need — and it is exactly the mechanism by which a previous review round's fix was discarded
silently. `droppedByPreference` was *added by a review* to answer a member's question about
their own E-Blast. Narrowing the port deleted the answer without deleting a line of the code
that computes it.

The same shape produced S56: `BuildAudienceTickDeps` has no `plansBridge`, so the AS5 audit is
not omitted — it is unrepresentable.

**What this costs at review time:** "diff the two paths and list what the new one doesn't call"
finds S4–S12 and misses these. The question that finds them is *what could the old path express
that the new type cannot?* Worth asking on any future rewrite-as-sibling, which on this branch
is how all 56 findings began.

### Where the fix diverged from the finding

**U1 / S9 — the measurement changed the shape of the answer.** The review asked
whether `contacts.remove` deletes or detaches. Measured: it **detaches**, while
answering `{"deleted": true}`. So the Art. 17 cascade had been reporting success
for addresses that were still at the processor — on both dispatch paths, wider
than the S9 the review wrote. An audience-less `DELETE /contacts/{email}` was
measured to delete for real, and is implemented as `deleteContactGlobally`.

It is **deliberately not called.** One Resend account serves every tenant, so
two tenants whose members share an address share one contact record; a global
delete during tenant A's erasure destroys tenant B's record and the Resend-side
unsubscribe flag with it — an Art. 21 regression on an uninvolved person, traded
for an Art. 17 residual. `erase-member-subprocessor-cascade.test.ts` case 2
caught this after the global delete was already wired and typechecking clean.
Recorded as residual 8a in the processing register; closing it needs a
cross-tenant live-holder check, which is an architectural decision.

**S2 — not a defect.** The ceiling change is deliberate and its reasoning is in
`reviews/cutover.md` § 5. What was wrong was every sentence explaining it. The
security finding's artefact half was right; its "unintended regression" framing
was not.
