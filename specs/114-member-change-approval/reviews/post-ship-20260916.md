## T120 — a coalesced resubmit dropped the reviewer's email

**Finding #1.** `submit-change-request.ts` coalescing (FR-011) makes a resubmit within 1 h inherit
`staff_notified_at` and queue NO outbox row. The dispatcher's staff arm
(`outbox-dispatch/route.ts`) then found the queued row's request `withdrawn / replaced` and
permanently failed it as `request_superseded`. Nobody was emailed until the next submission an
hour later.

**RED** (live, `tests/integration/members/change-requests-staff-email-dispatch.test.ts`, new case
"a resubmit INSIDE the coalescing window…"):

```
AssertionError: {"attempts":1,"lastError":"request_superseded"}: expected 'permanently_failed' to be 'sent'
```

**Fix.** New Application helper `resolveStaffEmailTarget(queued, load)` — follows
`replacedByRequestId` to the pending head (bounded at `MAX_REPLACEMENT_HOPS = 10`, so a cyclic
pointer cannot loop a cron tick) and renders that head **only when it INHERITED the queued row's
`staffNotifiedAt`**. That equality is exactly "coalesced, therefore no row of its own"; a
replacement past the 1 h window stamps its own time and HAS its own row, so the queued row stays
`request_superseded` and the reviewer never gets two identical emails. Withdrawn-by-member,
erasure-closed and decided requests stay `request_superseded`; a hard-deleted successor is
`request_gone`; a repo fault keeps the row on the retry ladder.

**GREEN**: the live suite 7/7, including the pre-existing reliability I-4 case (a replacement
PAST the window still leaves the earlier row `permanently_failed / request_superseded`).

**Mutation proof** of the no-duplicate guard: dropping the stamp comparison (always render the
head) turns that I-4 case red — `expected 'sent' to be 'permanently_failed'`. Restored.

**Files**: `src/modules/members/application/use-cases/change-requests/resolve-staff-email-target.ts`
(new) · `src/modules/members/index.ts` (barrel) · `src/app/api/cron/outbox-dispatch/route.ts` ·
`tests/unit/members/change-requests/resolve-staff-email-target.test.ts` (new, 10 cases) ·
`tests/integration/members/change-requests-staff-email-dispatch.test.ts`.

**Note on order**: the helper and its unit suite were written together (the unit suite was green
on first run). The behavioural RED is the live case above, and the guard is mutation-proved.

## T121 — an `Idempotency-Key` was unusable for 24 h after a 429 / 500

**Finding #2.** `portal/change-requests/route.ts` reserves the key before the use case;
`classifyIdempotencyRequest` reads a reserved-but-unwritten record as a CONFLICT
(`src/lib/idempotency.ts` ~129/172/221). The `rate_limited` and `server_error` arms returned
without remembering AND without releasing, so the client's correct retry — same key, same body —
answered 422 `idempotency-key-reused` for the record's whole 24 h TTL.

**RED** (`tests/contract/portal/change-requests-submit.test.ts`):

```
AssertionError: expected "spy" to be called with arguments: [ Anything, 'idem-429' ]
AssertionError: expected "spy" to be called with arguments: [ Anything, 'idem-retry' ]
```

**Fix.** New `releaseIdempotencyRecord(tenant, key)` in `src/lib/idempotency.ts` (a `redis.del`,

a 500). The route calls it on the 429 arm and on the 500 arm; the comment at the old ~209 now
states the mirror rule (deterministic refusal → remembered; transient → released). A deterministic
422 is still remembered and NOT released — pinned.

**GREEN**: 28/28 in that file; the replace suite 6/6.

**Other callers**: the `withIdempotency` helper and the plans / members / contacts routes were
checked. They are unaffected by this change (no new behaviour), but the same class exists wherever
a route reserves and then returns a transient refusal without releasing — **not swept here**; see

**Files**: `src/lib/idempotency.ts` · `src/app/api/portal/change-requests/route.ts` ·

## T122 — the portal form minted a fresh key per attempt

**Finding #3.** `portal-change-request-form.tsx` ~278 called `crypto.randomUUID()` inside
`onSubmit`, so the header bought nothing it was added for: a double-click or a retry after a
dropped response reached the server as two distinct requests — and the second REPLACED the first
(one-pending-per-submitter), burning one of the member's ten daily submissions.

**RED** (`tests/unit/members/presentation/portal-change-request-form.test.tsx`, new file):

```
AssertionError: expected '329d8498-…' to be '0b09f463-…'   (429 → retry carries a different key)
AssertionError: expected 'ee75e85b-…' to be '34af0e0c-…'   (500 → retry carries a different key)
```

**Fix.** One key per submission ATTEMPT SEQUENCE: minted lazily into a `useRef` (never during
render, so a StrictMode remount just mints on first use), reused across double-clicks, network
drops, 429s and 5xx, and cleared only on a TERMINAL outcome — any 2xx or a validation 422, both of
which the server remembers under the key.

**GREEN**: 4/4 new + the two existing form suites (5) unchanged.

## T123 — a partial address group was widened into a clear

**Finding #4.** `field-rules.ts` `fillLines` filled every omitted line with `null`, so an API
client proposing `{ registered_address: { city: 'Bangkok' } }` silently proposed CLEARING the
other five lines, and the reviewer saw a legitimate-looking "clear this line" diff.

**RED** (`tests/unit/members/change-requests/field-rules-parity.test.ts`):

```
AssertionError: expected true to be false    // the partial group was ACCEPTED
```

**Fix.** `refuseMissingLines` — when an address group is present every line KEY must be present
(its value may be `null`, which is the explicit clear); a missing line is an issue on that line
(`address_line_missing`). It runs FIRST on the billing group and short-circuits the value-level
`billing_address_incomplete` rule, so a path never carries two issues. The browser form is
unaffected: `buildProposalBody` always sends the whole object with `null`s.

**Behaviour change, deliberate**: three existing cases in that file encoded the old widening and
were rewritten to the new contract (the value-level group rule is re-pinned separately on a
COMPLETE object whose required lines are null, so nothing was lost).

**GREEN**: 16/16.

## T125 — the reason CHECK did not cover `partially_approved`

**Finding #6.** `0300` wrote `CHECK ("outcome" IS DISTINCT FROM 'rejected' OR "decision_reason" IS
NOT NULL)`, but FR-014 owes a reason whenever ANY field is rejected — which a
`partially_approved` decision does by definition.

**RED** (live, same file):

```
AssertionError: the UPDATE must be refused by the CHECK: expected undefined to be defined
```

**Fix.** `drizzle/migrations/0303_member_change_requests_reason_partial_ck.sql` — a `DO $$` pre-check
that RAISEs `member_change_requests_partially_approved_without_reason` (ERRCODE
`check_violation`) if any existing row would violate, then `DROP CONSTRAINT IF EXISTS` +
`ADD CONSTRAINT` under the same name with

```sql
CHECK ("outcome" NOT IN ('rejected', 'partially_approved') OR "decision_reason" IS NOT NULL)
```

(as `IS DISTINCT FROM` did); `approved` needs no reason; `rejected` still does. Journal entry
`idx 304`, `when 1798543600000` (the previous last entry is `0302` at `1798543500000`).

**Applied on the `dev` branch and read back** (`pg_get_constraintdef` over
`pg_constraint`):

```
member_change_requests_reason_iff_rejected_ck ::
  CHECK (((outcome <> ALL (ARRAY['rejected'::text, 'partially_approved'::text]))
          OR (decision_reason IS NOT NULL)))
```

**Canary** added to `scripts/verify-schema.ts` — it reads the PREDICATE, not just the name (the
constraint was re-created under the SAME name, so existence proves nothing). `pnpm db:verify` →
