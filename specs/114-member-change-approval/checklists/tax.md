# Thai Tax-Document Touchpoints Checklist: Member Portal — Approval Workflow for Member Changes

**Purpose**: Validate that the requirements covering the fields that feed Thai Revenue Code tax documents (§ 86/4 buyer name and address) are complete, clear, consistent and measurable before `/speckit.tasks`. Narrow gate — the feature issues no document and touches no amount; it changes *inputs* to future documents. `thai-tax-compliance-auditor` co-signs at `/speckit.review`.
**Created**: 2026-09-11
**Feature**: [spec.md](../spec.md) · [plan.md](../plan.md) · [data-model.md](../data-model.md) · `specs/088-invoice-tax-flow-redesign/`

**Note**: Generated by `/speckit.checklist`. `[x]` = reviewer judged the requirement text satisfactory; not implementation status.

## Requirement Clarity — which fields are tax-affecting

- [ ] CHK001 Is the set of tax-affecting proposable fields stated exactly — company name, billing address, and registered address *only when no billing address is on record* — and is that rule the same one the invoicing buyer block uses today (088)? [Consistency, Spec §FR-019, §FR-022, Data-model §3]
- [ ] CHK002 Is it specified whether the company name a member may propose is the *same* field printed as the buyer name on tax documents, and whether a Thai-script name or a separate legal-name field exists that is *not* proposable? [Ambiguity, Spec §FR-002 "company name"; Data-model §3 `members.company_name`] → closed: FR-019 / FR-022 + data-model § 2–3 (buyer block = legal_name / address / primary_contact_name at issue)
- [ ] CHK003 Is the interaction between a proposable billing address and the staff-only head-office / branch code stated — a billing address change cannot itself move the § 86/4 branch designation, and staff must review branch code separately? [Gap, Spec §FR-003 (branch staff-only), §FR-019] → closed: FR-019 (billing address never moves the branch designation; hint)
- [ ] CHK004 Is the billing-address *country* line's proposability reconciled with VAT treatment (a non-Thai billing address may change how a document is issued) and with the member's staff-only country field? [Ambiguity, Spec § Assumptions "billing address's country line", §FR-003] → closed: FR-019 + § Edge Cases "Non-Thai billing country"

## Requirement Completeness — document immutability

- [ ] CHK005 Is it stated that already-issued invoices, receipts and credit notes keep their frozen buyer block regardless of approval, with a measurable criterion (SC-012 before/after comparison)? [Measurability, Spec §FR-022, §SC-012, §US2 AS6]
- [ ] CHK006 Is the "document in flight" case defined — a draft invoice created before approval and issued after — i.e. which values the issued document carries and that no rewrite happens? [Gap, Panel § Unverified 3; Spec § Edge Cases covers "issued while pending" only] → closed: FR-022 (buyer block built at issue; drafts carry approved values)
- [ ] CHK007 Is the approval of a company name explicitly decoupled from tax ID (staff-only): a proposed name that no longer matches the DBD registration of the frozen tax ID is a staff verification concern, and is that verification stated as a requirement or an assumption? [Assumption, Spec § Assumptions "Company name changes are rare and legitimate"]

## Requirement Clarity — staff review support

- [ ] CHK008 Is the "affects tax documents" flag required on the review page, the staff email and the history — and does it carry the *reason* (which document field it feeds) so a reviewer knows what to check against DBD? [Completeness, Spec §FR-019, Contract notifications §1]
- [ ] CHK009 Is a DBD-verification step for company name / address recorded as chamber policy (runbook or review-page hint) rather than a system control, and is the follow-up feature for tax-block proposals with a DBD check scoped out clearly? [Clarity, Spec § Out of Scope, Research R14]
- [ ] CHK010 Are Buddhist-Era display rules stated for any date shown on tax-affecting rows (display-only; storage Gregorian UTC)? [Consistency, Plan Constitution V]
