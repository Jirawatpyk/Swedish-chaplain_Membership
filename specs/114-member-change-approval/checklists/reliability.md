# Reliability Requirements Checklist: Member Portal — Approval Workflow for Member Changes

**Purpose**: Validate that the reliability requirements — transactions, concurrency, idempotency, notification delivery, audit truth, rollback — are complete, clear, consistent and measurable before `/speckit.tasks`. Formal gate; `reliability-guardian` + `drizzle-migration-reviewer` co-sign at `/speckit.review`.
**Created**: 2026-09-11
**Feature**: [spec.md](../spec.md) · [plan.md](../plan.md) · [data-model.md](../data-model.md) · [contracts/](../contracts/) · [research.md](../research.md)

**Note**: Generated by `/speckit.checklist`. `[x]` = reviewer judged the requirement text satisfactory; not implementation status.

## Requirement Clarity — transactional boundaries

- [ ] CHK001 Is the submit unit of work enumerated (lock previous pending → withdraw/replace → insert request + fields → audit → outbox rows) with the rule that every refusal after the first write rolls back? [Completeness, Research R3, R8, Contract portal §2]
- [ ] CHK002 Is the decide unit of work enumerated (FOR UPDATE request + member → guards → re-validate → apply approved fields → per-field outcomes + decision → audit → outbox) with the explicit prohibition on `return err()` inside the tx? [Completeness, Spec §FR-015, Research R4]
- [ ] CHK003 Is the "all-or-nothing" requirement measurable — i.e. is a test named in which the second field's write fails and the assertion is *nothing applied, no decision, request still pending*? [Measurability, Spec §US2 AS9, Research R16]
- [ ] CHK004 Is it stated that the outbox rows are enqueued on the *same* tx (so a failed commit enqueues nothing and a committed decision always has its notification queued)? [Consistency, Spec §FR-012, §FR-024]

## Requirement Completeness — concurrency

- [ ] CHK005 Is the one-pending-per-submitting-person invariant given a database-level guarantee (partial unique index) in addition to the application lock, and is the ×N same-submitter race test named? [Completeness, Spec §FR-008, Research R3, R16]
- [ ] CHK006 Is the two-reviewer race resolved by a stated rule (FOR UPDATE + state check; the loser gets `already_decided` with reviewer + outcome) rather than "exactly one decision is recorded"? [Clarity, Spec §FR-018, Contract admin §3]
- [ ] CHK007 Is the **withdraw-vs-decide** race stated explicitly — first committed action wins; the other is refused (`not_pending` / `already_decided`) — rather than being inferable from FR-009 + FR-017? [Gap, Spec §FR-009, §FR-017] → closed: FR-017 + § Edge Cases
- [ ] CHK008 Is the **resubmit-vs-decide** race defined: a decision that lands while the member is submitting a replacement — does the replacement withdraw a request that is now decided (must not), and what does the member see? [Ambiguity, Spec §US5 AS4, §FR-008] → closed: FR-008 (replace only a still-pending request)
- [ ] CHK009 Is behaviour defined when a proposed *contact* field's contact has been removed/unlinked between submission and decision (apply refused? field auto-rejected? request closed)? [Gap, Spec § Edge Cases covers archived/erased member only] → closed: FR-020 + admin contract `undecidable: contact_removed`
- [ ] CHK010 Is behaviour defined when an approved field's proposed value equals the current value at decision time (staff made the same change meanwhile) — no-op write, still recorded as approved? [Gap, Spec §FR-019 shows the three values but does not say what apply does] → closed: FR-015 + admin contract `alreadyCurrent`

## Requirement Clarity — idempotency & finality

- [ ] CHK011 Is "repeated identical decision" defined by a concrete equality (same request id + same per-field decisions + same reason) so the no-op path is testable, and is a *different* repeat required to be refused with `already_decided`? [Clarity, Spec §FR-017, Contract admin §3]
- [ ] CHK012 Is submit idempotency stated for the retry case (client retries after a timeout) — `Idempotency-Key` semantics or the "identical to pending → already_pending" rule — so a retry cannot create two requests or two staff emails? [Completeness, Spec §FR-007, Contract portal §2]
- [ ] CHK013 Is the finality rule complete — decided and withdrawn are terminal for *every* transition (decide, withdraw, replace, erasure-close), with the response for each attempted transition named? [Completeness, Spec §FR-017, Data-model §4]

## Requirement Completeness — notifications

- [ ] CHK014 Is the delivery guarantee stated as at-least-once ("one notification *queued*") everywhere the spec says "one email", so no test asserts exactly-once delivery? [Consistency, Spec §FR-011, §FR-023, §SC-013, Clarifications U6]
- [ ] CHK015 Is the coalescing window anchored to the last *queued staff notification* (inherited on replacement), so a chain of resubmissions every 59 minutes cannot suppress notification indefinitely, and is that bound stated? [Edge Case, Spec §FR-011, Research R8]
- [ ] CHK016 Is per-recipient failure isolation stated (one reviewer's bounce does not block the others; retry + `email_dispatch_failed` audit) and the "no reviewer exists" case handled (request still created, warning logged)? [Completeness, Spec § Edge Cases "Staff email cannot be delivered", "No staff user is entitled to review"]
- [ ] CHK017 Is the "recipient gone" case for the member email (contact removed/erased before dispatch) specified with its audit and no fallback to another address? [Completeness, Contract notifications §1]
- [ ] CHK018 Is the read-at-send design stated as a requirement (dispatcher renders from request rows) so a scrubbed or replaced request cannot send stale values, and is the dispatcher's tenant-context need (V3) carried as a verify-before-task item? [Consistency, Research R8, V3]

## Requirement Completeness — audit truth & data integrity

- [ ] CHK019 Are the actor rules stated per event (member user / reviewer / system on erasure) with the `check:actor-role-truth` gate named, so no row can state a role its actor did not hold? [Completeness, Spec §FR-025, Contract notifications §2]
- [ ] CHK020 Are the CHECK constraints tying `state` ↔ `outcome` ↔ `decided_*` ↔ `withdrawn_reason` stated so an inconsistent row is impossible by construction? [Completeness, Data-model §1 CHECKs]
- [ ] CHK021 Is the address-group atomicity rule (all lines proposed/applied together, never line-by-line) stated for storage, decision and apply? [Consistency, Spec § Edge Cases "Address groups", Data-model §2]
- [ ] CHK022 Is the rate cap's source of truth (durable count over the request table) and its independence from Redis stated as a requirement with a test that runs with the limiter absent? [Measurability, Spec §FR-008, §SC-013, Research R9, R16]

## Requirement Completeness — migration, flag & rollback

- [ ] CHK023 Is migration 0300 specified as forward-only (enum `ADD VALUE` is irreversible) with the pre-check and the journal `when` uniqueness rule, and is "apply + integration test before commit" named as the discipline? [Completeness, Data-model §6, CLAUDE.md § Gotchas]
- [ ] CHK024 Is the rollback path layered and stated — tenant setting OFF (immediate, audited, rows stay decidable) → platform flag OFF (routes 404, form reverts, rows retained) — with what each layer does to pending rows, banners and counts? [Completeness, Spec §FR-031, §FR-032, Quickstart § 3]
- [ ] CHK025 Is flag-OFF byte-identity of the F3 self-service path stated as a regression criterion (existing `profile.test.ts` suite must pass unchanged)? [Measurability, Spec §SC-011]
- [ ] CHK026 Are the reused mechanisms' change costs enumerated as requirements on the plan (outbox enum + dispatcher arms, audit enum × 5 places, `check:multi-tenant` registration, gauges tick generalisation, settings write path + audit) so none is discovered at implementation? [Completeness, Research R7, R8, R11, R12]
