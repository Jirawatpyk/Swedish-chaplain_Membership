> The 15 Criticals collapse into 5 root causes (multiple lenses found the same defect independently):
> 1. **users_last_admin_protection trigger breaks on `DROP COLUMN role`** — total auth outage; trigger also guards an empty set between PR 1 (admin→super_admin promotion) and PR 5.
> 2. **Contract migration bundled with code deploy** — Vercel migrates at build while the old deployment (whose Drizzle schema still SELECTs `role`) serves traffic → 500s for the whole build window. Needs 3-deploy staging.
> 3. **Session-path permission JOIN bypasses RLS** — the spec's "existing single session query" claim is factually wrong; the join would run on the pool-global BYPASSRLS connection outside runInTenant.
> 4. **Staff pages have no positive permission gate** — requireSession only deny-lists `member`; adding a 4th staff role exposes money pages by direct URL; plus ~15 fail-open `role === 'manager' ? 'manager' : 'admin'` coercions that escalate unknown roles to admin.
> 5. **`superAdminOnly` enforced only at write time** — seed bugs, Reset-to-default, or operator SQL can grant super-admin-only permissions; the evaluator must also refuse.

## Critical (15)

### [architecture · CONFIRMED] sec-enum-drop-breaks-last-admin-trigger

- **Section**: §5 Data model (expand-contract step 3) / §9 PR 5
- **Claim**: Dropping the `users.role` pgEnum column in the PR-5 contract migration silently breaks the `users_last_admin_protection` plpgsql trigger, which makes EVERY `UPDATE` and `DELETE` on `users` fail at runtime — a total auth outage. The spec never mentions the trigger.
- **Failure scenario**: `CREATE TRIGGER users_last_admin_protection BEFORE UPDATE OR DELETE ON users FOR EACH ROW` (drizzle/migrations/0003_last_admin_protection_trigger.sql:84-87) executes a function whose body dereferences `OLD.role` / `NEW.role` and runs `SELECT COUNT(*) FROM users WHERE role = 'admin'` (0004_fix_last_admin_trigger_delete_return.sql:21-31). plpgsql resolves those at execution time, so `ALTER TABLE users DROP COLUMN role` succeeds without complaint and then every subsequent write raises `record "old" has no field "role"`. Concretely: a user signs in → `sign-in` updates `last_sign_in_at` / `failed_signin_count` on `users` → trigger fires → exception → sign-in returns 500. Nobody can authenticate, including the Super Admin who would fix it. `countActiveAdmins()` (src/modules/auth/infrastructure/db/user-repo.ts:417) breaks in the same instant.
- **Recommendation**: Add an explicit trigger-migration step to §5. PR 1 must ship a replacement `users_last_admin_guard()` keyed on the new `role_id` (guarding 'last active super_admin' per §6.2 invariant 3) — note the DB comment on 0003 says disabling it requires Principle I sign-off, so replacement (not removal) is the only compliant path. The PR-5 migration must `CREATE OR REPLACE FUNCTION` (or `DROP TRIGGER`) in the SAME .sql file as the `DROP COLUMN`, before the drop. Add an integration test on live Neon that demotes/deletes the last super_admin AND performs an ordinary `users` UPDATE after the contract migration.
- **Evidence**: drizzle/migrations/0003_last_admin_protection_trigger.sql:44-59,84-87; drizzle/migrations/0004_fix_last_admin_trigger_delete_return.sql:21-31; src/modules/auth/infrastructure/db/user-repo.ts:417,629

### [architecture · CONFIRMED] ops-contract-migration-ships-with-code

- **Section**: §5 (expand-contract) / §9 PR 5
- **Claim**: PR 5 bundles the `DROP COLUMN role` contract migration with feature code in one deploy. Vercel runs migrations at build time while the PREVIOUS deployment still serves traffic, so the old code — which still selects `users.role` — hits a dropped column for the whole build-and-promote window.
- **Failure scenario**: `vercel-build` runs `run-migrations.ts && next build`; the PR-4 deployment is live and serving during that window. Its `userRepo.findById` projection includes `role: row.role` (src/modules/auth/infrastructure/db/user-repo.ts:77) and `countActiveAdmins()` issues `WHERE users.role = 'admin'` (:417), so every `getCurrentSession()` on the old deployment starts throwing `column "role" does not exist` from the moment the migration commits until the new deployment is promoted. Result: authenticated 500s across /admin and /portal on a live, launched tenant with real money flows. The spec itself names this constraint in §5 and then violates it.
- **Recommendation**: Split PR 5 into PR 5a (code only: stop reading `users.role` / `invitations.intended_role` everywhere; deploy; verify) and PR 5b (migration only, no code change: drop the columns + replace the trigger). Never put a destructive DDL in the same deploy as the code that stops depending on it. State this rule explicitly in §5 so /speckit.tasks orders it correctly.
- **Evidence**: CLAUDE.md § Gotchas (prod auto-migrates on deploy via `vercel-build`); src/modules/auth/infrastructure/db/user-repo.ts:77,417; docs/superpowers/specs/2026-08-10-rbac-permission-system-design.md:104,113,200

### [compliance · CONFIRMED] sec-last-admin-db-trigger-broken-by-role-enum-drop

- **Section**: §5 Expand-contract step 3 + §6.2 invariant 3 + §9 PR 5
- **Claim**: PR 5 drops the `role` pgEnum columns, but the DB-level `users_last_admin_protection` trigger reads `OLD.role` / `NEW.role` and queries `WHERE role = 'admin'` literally — dropping the column either fails the migration or, if the trigger is dropped with it, removes the only race-free lockout guarantee and replaces it with an application-layer check that migration 0003's own header documents as non-atomic.
- **Failure scenario**: Two live-prod failure modes. (a) `ALTER TABLE users DROP COLUMN role` on a production Vercel build fails or leaves `users_last_admin_guard()` referencing a dropped column, so every UPDATE/DELETE on `users` raises — sign-in's `last_seen_at`/lockout writes and every account-lifecycle route break while the old deployment is still serving traffic. (b) If the trigger is simply dropped, §6.2 invariant 3 ("Domain-enforced") reintroduces exactly the race migration 0003 was written to close: two concurrent demote/disable requests each read `count = 2`, both pass, and the tenant is left with zero super_admins — unrecoverable from the UI because `users:manage` and `roles:manage` are super-admin-only. It also breaks GDPR erasure error handling: `erase-user.ts` catches SQLSTATE 23514 from this trigger to return the distinct `erase-user-last-admin` code; without the trigger, erasing the last super_admin's linked account succeeds and locks the tenant out instead of refusing.
- **Recommendation**: Make the trigger rewrite a first-class, blocking deliverable of the same migration that drops the enum column: replace `users_last_admin_guard()` with a version that joins `users.role_id → roles` and counts active users whose role key is `super_admin`, and keep `SQLSTATE 23514` so `isLastAdminTriggerError` and the `erase-user-last-admin` path keep working unchanged. Add a live-Neon integration test that concurrently demotes the last two super_admins and asserts exactly one succeeds. Do not ship PR 5 before that test is green.
- **Evidence**: drizzle/migrations/0003_last_admin_protection_trigger.sql (function body: `OLD.role = 'admin'`, `SELECT COUNT(*) … WHERE role = 'admin' AND status = 'active'`; header: "NOT inside a single transaction… two concurrent demote-the-last-admin requests can both observe count = 2"); src/modules/auth/application/erase-user.ts:43-58,154-160; src/lib/db-errors.ts `isLastAdminTriggerError`

### [compliance · CONFIRMED] sec-permission-join-runs-outside-tenant-context

- **Section**: §6.1 Request path
- **Claim**: The spec's request path — "session lookup (existing single query) → JOIN roles + role_permissions in that same query" — is factually wrong about the existing code and, as written, would read tenant-scoped RLS+FORCE tables from a connection that has no tenant context and runs as a BYPASSRLS role, violating Principle I's two-layer isolation on the permission-decision path itself.
- **Failure scenario**: Session lookup is not one query and is not tenant-scoped: `getCurrentSession()` issues `sessionRepo.findById` then a separate `userRepo.findById`, both on the pool-global `db` singleton, outside `runInTenant`. That singleton connects with the Neon integration role, which has `rolbypassrls = TRUE` — `runInTenant` exists precisely to `SET LOCAL ROLE chamber_app` because without it "the RLS policies are a no-op". Adding a JOIN onto `roles` / `role_permissions` there means the DB layer of tenant isolation is disabled for the single query that decides what every request is allowed to do, and no `app.current_tenant` GUC is set. This is the F7.1a incident class the spec itself cites in §5. The alternative failure is equally bad: if the JOIN is instead threaded through `chamber_app` without the GUC, FORCE RLS returns zero rows, every staff PermissionSet is empty, and the entire staff portal is locked out in live prod. Compounding it, `users` is cross-tenant (no `tenant_id`, no RLS) while `roles` is tenant-scoped, so `users.role_id` is a foreign key from an unscoped table into an RLS-scoped one with no stated ON DELETE and no stated tenant-consistency constraint.
- **Recommendation**: Correct §6.1 to describe the real path and specify the tenant scoping explicitly: resolve the tenant first (`resolveTenantFromRequest`), then load the PermissionSet inside `runInTenant(ctx, tx => …)` so `SET LOCAL ROLE chamber_app` + `app.current_tenant` are in force, and grant `chamber_app` SELECT on `roles` / `role_permissions`. State whether `users.role_id` gets a tenant-consistency check (e.g. a `role_tenant_id` shadow column with a composite FK to `roles(tenant_id, id)`), and make the mandatory cross-tenant probe test in §9 cover the *session-path* permission read, not only direct table reads.
- **Evidence**: src/lib/auth-session.ts:62,77 (two separate repo calls); src/lib/db.ts:60-65 (global `db` on the owner connection), :74-81 ("Neon's default integration role (`neondb_owner`) has `rolbypassrls = TRUE`, which silently disables ENABLE/FORCE ROW LEVEL SECURITY"), :266-268 (the three SET LOCALs); src/modules/auth/infrastructure/db/schema.ts:723-758 (`users` has no tenant_id); drizzle/migrations/0006_plans_and_fee_config.sql:147 (chamber_app has SELECT on users)

### [datamodel · CONFIRMED] crit-drop-role-breaks-last-admin-trigger

- **Section**: § 5 Expand-contract step 3 / § 9 PR 5 (contract migration, "drop the `role` pgEnum columns")
- **Claim**: Dropping `users.role` silently decapitates the `users_last_admin_protection` trigger, whose plpgsql body reads `OLD.role`/`NEW.role`, turning every subsequent UPDATE/DELETE on `users` into a runtime error — including the sign-in path.
- **Failure scenario**: PostgreSQL does not dependency-track column references inside plpgsql function bodies, so `ALTER TABLE users DROP COLUMN role` SUCCEEDS. The trigger `users_last_admin_protection` is `BEFORE UPDATE OR DELETE ON users FOR EACH ROW` and unconditionally evaluates `OLD.role = 'admin'`. The very next `UPDATE users SET last_sign_in_at = …` (user-repo.ts:370) or `SET failed_signin_count` (:397) raises `record "old" has no field "role"` (SQLSTATE 42804). Sign-in, lockout counters, disable/enable and every last-admin path fail for 100% of users on live prod, unrecoverable without an emergency hotfix migration. Separately, even before the drop, D7 makes the trigger vacuous: once no row has `role='admin'` the guard never fires, so the DB-layer race protection that migration 0003 exists for is silently lost while § 6.2.3 "last-super-admin protection" is app-layer only — exactly the race 0003's header says the app layer cannot close.
- **Recommendation**: In the SAME migration that drops the column, and BEFORE the DROP statement, `CREATE OR REPLACE FUNCTION users_last_admin_guard()` rewritten against the new column, e.g. gate on `OLD.role_id = (SELECT id FROM roles WHERE tenant_id = … AND key = 'super_admin')` and count remaining `status='active'` holders of that role_id. Add an integration test that performs an `UPDATE users SET last_sign_in_at = now()` after the migration — the current suite would not catch this because no test updates users post-drop. Also add the DB-layer last-super-admin guard to § 6.2.3 explicitly; app-layer only is a regression against 0003.
- **Evidence**: drizzle/migrations/0004_fix_last_admin_trigger_delete_return.sql:16-49 (function body reads OLD.role/NEW.role); drizzle/migrations/0003_last_admin_protection_trigger.sql:84-87 (BEFORE UPDATE OR DELETE ON users FOR EACH ROW); drizzle/migrations/0003_last_admin_protection_trigger.sql:1-17 (rationale: app-layer countActiveAdmins is not atomic); src/modules/auth/infrastructure/db/user-repo.ts:370,397,618,629 (UPDATEs on users on the sign-in path)

### [datamodel · CONFIRMED] crit-contract-migration-vs-old-deployment

- **Section**: § 5 Expand-contract ("Vercel runs migrations at build while the old deployment still serves traffic") / § 9 PR 5
- **Claim**: The contract step drops `users.role` in the same PR as the code that stops referencing it, so during the whole `next build` + deploy window the OLD deployment issues `SELECT … "users"."role" …` against a table that no longer has the column.
- **Failure scenario**: `vercel-build = run-migrations.ts && next build` — the migration COMMITS first, then the build runs for minutes, and the previous deployment serves the entire time. Drizzle's `db.select().from(users)` emits an explicit column list derived from `schema.ts`, so the old deployment selects `role` whether or not any application code reads the field. Result: every `userRepo.findById` (called on every authenticated request via getCurrentSession) raises `column users.role does not exist` (42703) → total 500 on sign-in and every protected page on live prod, with real members and money in flight. The spec's own mitigation ("After PR 2 no call site reads the role enum directly") does not help, because the hazard is the generated column list, not the call sites. Symmetrically, PR 2's code cannot stop WRITING `role` either: the column is `NOT NULL` with no default, so a PR-2 `createPending` that omits it fails — the expand migration never relaxes it.
- **Recommendation**: Split the contract into three deploys and say so in § 5: (1) expand migration ALSO does `ALTER TABLE users ALTER COLUMN role DROP NOT NULL` (and same for `invitations.intended_role`); (2) a code-only deploy removes `role` from `schema.ts` and every writer, so nothing selects or writes it; (3) a migration-only deploy, at least one deploy later, does `ALTER TABLE users DROP COLUMN role`. Same three-step for `invitations.intended_role`. Never co-locate the schema.ts removal and the DB DROP in one PR.
- **Evidence**: package.json: `vercel-build = node --import tsx scripts/run-migrations.ts && next build --turbopack`; src/modules/auth/infrastructure/db/user-repo.ts:347 (`db.select().from(users)`), :655-660 (comment confirming the getTableColumns-spread select shape), :629 (`db.update(users).set({ role })`), :413-417 (countActiveAdmins reads users.role); src/lib/auth-session.ts:62,77,86 (session path hits users on every request); src/modules/auth/infrastructure/db/schema.ts:728 (`role: roleEnum('role').notNull()`)

### [datamodel · CONFIRMED] crit-session-join-bypasses-rls

- **Section**: § 6.1 Request path ("JOIN roles + role_permissions in that same query")
- **Claim**: Joining the FORCE-RLS `roles`/`role_permissions` tables into the session lookup executes on the global `db` pool, which does not `SET LOCAL ROLE chamber_app` or `SET LOCAL app.current_tenant` — so the permission read has no DB-layer tenant isolation at all, while the mandatory cross-tenant probe test still passes.
- **Failure scenario**: Two-horned failure. (a) The pool connection role is BYPASSRLS, so the join reads permission rows for every tenant with zero enforcement — precisely the F7.1a incident class CLAUDE.md Gotchas warns about, and it means Principle I's second layer is absent on the single hottest code path in the app. (b) If the pool role is ever not BYPASSRLS (Neon owner rotation, an ops role change, the 2026-07-17 `row_security` contamination class already documented in db.ts), then FORCE RLS with a policy scoped `TO chamber_app` matches no policy for the connecting role → the join returns ZERO rows → every user gets an empty PermissionSet → whole-tenant lockout with no super-admin escape (the code bypass in § 3 keys on the role row, which is exactly what came back empty). The § 10 probe test is written against `roles`/`role_permissions` directly under `runInTenant`, so it verifies a path production does not use — it would go green while the real read path bypasses RLS.
- **Recommendation**: Specify that the PermissionSet load runs inside `runInTenant(ctx, tx => …)` as its own step (accepting the extra round-trip), never as a join off the global users/sessions query. State in § 10 that the cross-tenant probe must exercise the production loader function itself (the same code the request path calls), not an ad-hoc query against the tables — otherwise the Review-Gate blocker test is vacuous. Add a DEBUG_RLS_STATE-style assertion or an integration test that the permission read fails closed when `app.current_tenant` is unset.
- **Evidence**: src/lib/auth-session.ts:58-89 (getCurrentSession → sessionRepo.findById + userRepo.findById, no tenant context); src/modules/auth/infrastructure/db/user-repo.ts:23,347 (global `db` singleton, not runInTenant), :247 ("tenant_id, no RLS — so it cannot join a members `runInTenant` tx"); src/lib/db.ts:256-268 ("the connection role is BYPASSRLS"; runInTenant is what drops to chamber_app + sets app.current_tenant); drizzle/migrations/0006_plans_and_fee_config.sql:117 (`CREATE ROLE chamber_app NOLOGIN NOBYPASSRLS`); drizzle/migrations/0186_f9_smart_insight_dismissals.sql:44-52 (canonical FORCE RLS + policy `TO chamber_app`)

### [reality · CONFIRMED] sec-session-join-bypasses-rls

- **Section**: § 6.1 Request path / § 5 Data model
- **Claim**: The prescribed "session lookup → JOIN roles + role_permissions in that same query" runs on the pool-global `db` singleton (BYPASSRLS owner role) outside any `runInTenant`, so the most security-critical read in the system would resolve tenant-scoped permission rows with BOTH isolation layers disabled — and `users.role_id` is a cross-tenant FK into a tenant-scoped table.
- **Failure scenario**: `getCurrentSession()` calls `sessionRepo.findById` and `userRepo.findById`, both of which use the module-level `db` client, not a `runInTenant` tx. Tenant policies in this repo are written `TO chamber_app` and rely on `SET LOCAL ROLE chamber_app` + `SET LOCAL app.current_tenant`; neither is issued on this path. A `users` row (global identity, no `tenant_id`, no RLS) carrying `role_id` that points at tenant B's `roles` row would resolve tenant B's permission set for a tenant A request, and the `super_admin` code bypass (§ 3) turns that into full platform escalation. There is also no cross-tenant probe test possible for a read that never enters a tenant context, which is a Review-Gate blocker under Principle I sub-clause 3.
- **Recommendation**: Do not resolve permissions on the un-tenanted session path. Either (a) keep `roles`/`role_permissions` cross-tenant like `users` and drop the RLS claim (documenting the deviation in plan.md § Complexity Tracking), or (b) keep them tenant-scoped and resolve the PermissionSet in a separate `runInTenant(ctx, tx => …)` call after `resolveTenantFromRequest`, with an explicit assertion that `roles.tenant_id` matches the request tenant. Add the mandatory two-direction cross-tenant probe test either way.
- **Evidence**: src/lib/auth-session.ts:62,77,86 (three separate global-`db` calls); src/lib/db.ts:65 (`export const db`), src/lib/db.ts:240-268 (`runInTenant` is the only place ROLE/GUC are set); drizzle/migrations/0185_f9_tables.sql:40-45 (policy `TO chamber_app` USING `tenant_id = current_setting('app.current_tenant', TRUE)`); src/modules/auth/infrastructure/db/schema.ts:723-758 (`users` has no `tenant_id`); docs/saas-architecture.md:143 ("F1 `users` table does NOT have RLS"); .specify/memory/constitution.md:368-373

### [reality · CONFIRMED] mig-drop-role-column-breaks-last-admin-trigger

- **Section**: § 5 Expand-contract step 3 / § 9 PR 5
- **Claim**: "Drop the `role` pgEnum columns" would silently break the DB trigger `users_last_admin_protection`, whose plpgsql body reads `OLD.role`/`NEW.role`, taking down every write to `users` — including the `last_sign_in_at` update on every successful sign-in.

Compounding it: D7 promotes existing admins to `super_admin` at the role_id layer while the enum column still says `admin`, so during PRs 2-4 the trigger protects a stale column that no longer reflects who the real super admins are.
